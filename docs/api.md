# HTTP API (`/api/v1`)

The REST surface for clients that cannot call a `createServerFn` — a mobile app, a script, another
service, or the browser fetching raw bytes.

A server function is **not** an HTTP API: its URL and payload envelope are generated by the compiler
for the web bundle's client stub, and an unauthenticated call throws `redirect({ to: "/login" })`
rather than returning a status. So a non-web client needs its own transport. What it does *not* need
is its own logic — an endpoint calls the same code the web calls, so the two cannot drift.

## Layering

```
routes/api/v1/**          transport: resolve actor, parse input, shape response   (2–4 lines)
lib/<feature>/service.ts  domain: business rules, access, transactions            (all the logic)
lib/db/functions.ts       generic builders: Drizzle, soft delete, tenancy, pagination
```

Most features start with their server functions colocated in the route folder (see `tasks`). Move a
feature to the three-layer shape — service in `src/lib/<feature>/`, thin RPC + REST transports on
top — when it gets a second transport, not before. See CLAUDE.md, "When a feature outgrows its route
folder".

Error handling is not the endpoint's job — see below. A new endpoint is only its happy path:

```ts
export const Route = createFileRoute("/api/v1/things/$id")({
  server: {
    middleware: [apiAuthMiddleware({ thing: ["view"] })],
    handlers: {
      GET: async ({ params }) => {
        const thing = await dbQueryBuilder(
          { table: "things", where: { id: params.id } },
          { first: true },
        );
        if (!thing) throw notFound("Thing not found");
        return json(thing);
      },
    },
  },
});
```

## Authentication

Every endpoint declares `middleware: [apiAuthMiddleware()]`
([src/lib/api/middleware.ts](../src/lib/api/middleware.ts)) — deliberately the same shape as
`authMiddleware()` on the web's server functions: same factory, same optional `PermissionCheck`,
same session on `context`, so a handler reads `context.user` exactly as a server function does.
Today that means the app's session cookie (`auth.session_token`). The one difference is the failure
mode: **401**, not `redirect({ to: "/login" })`, which a native client cannot follow.

The permission check is `assertPermission`, the same helper the server functions and services use,
so a grant cannot mean one thing here and another there. A feature on the three-layer split asserts
its grants inside the service and passes **no** permission here — re-declaring it in the route would
be redundant when it agrees and a lie when it doesn't.

**Bearer tokens are not enabled.** Adding better-auth's `bearer()` plugin to
[src/lib/auth/config.ts](../src/lib/auth/config.ts) makes `Authorization: Bearer <token>` work here
with no change to the middleware or to any endpoint — that is the whole reason session resolution
sits in one place.

## Choosing an organization

Every endpoint is scoped to one organization, and **the session decides which** — the same
`session.activeOrganizationId` the web app uses. There is no `X-Organization-Id` header and no
per-endpoint parameter: the middleware resolves the caller's membership and opens the tenant scope
that the generic builders read, so scoping lives in one place for both transports.

A client changes it by calling the organization plugin's own endpoint, which is already mounted by
the auth passthrough ([api/auth/$.ts](../src/routes/api/auth/$.ts)):

```
POST /api/auth/organization/set-active   { "organizationId": "…" }
GET  /api/auth/organization/list
```

A caller with no membership — or one whose session still points at an organization they have been
removed from — gets **403**, not an empty list. `resolveActor` re-reads the membership on every
request, so a removal takes effect on the next call rather than when the session expires.

## Response envelope

Success — always `{ data }`, status 200 unless noted (`json(...)` in
[src/lib/api/respond.ts](../src/lib/api/respond.ts)):

```json
{ "data": { "id": "abc", "title": "Write the report", "status": "todo" } }
```

Failure — always `{ error }`:

```json
{ "error": { "message": "You do not have permission to perform this action." } }
```

Validation failures add per-field messages:

```json
{ "error": { "message": "Invalid request", "fields": { "title": ["Title is required"] } } }
```

| Status | Meaning | Thrown by |
|---|---|---|
| 400 | malformed input, or an action illegal in the current state | `badRequest(…)`, zod |
| 401 | no session | `apiAuthMiddleware` |
| 403 | authenticated but not permitted, or no active organization | `forbidden(…)`, `assertPermission`, `requireTenantId` |
| 404 | no such row | `notFound(…)` |
| 500 | internal fault — logged server-side, never detailed to the client | anything not an `AppError` |

**Throwing is the error path — there is nothing to wrap.**
[`apiErrorMiddleware`](../src/lib/api/middleware.ts) is registered globally in
[src/start.ts](../src/start.ts) and applies `toErrorResponse` to every request under `/api/v1`. It
is global rather than per-route on purpose: a per-endpoint wrapper is a step you can forget, and
forgetting it is exactly the case that leaks a stack trace. Requests outside the prefix pass through
untouched, so a page error still gets TanStack's normal error boundary.

The errors themselves are `AppError`s from [src/lib/errors.ts](../src/lib/errors.ts)
(`badRequest` / `unauthorized` / `forbidden` / `notFound`). On the RPC side the same throw surfaces
its `message` in the client's toast, so domain code can throw them without knowing which transport
called it.

## Endpoints

| Method | Path | Notes |
|---|---|---|
| GET | `/api/v1/tasks/attachments/:id` | One task attachment's bytes. Requires `task: ["view"]`. |
| GET | `/api/v1/avatars/:file` | A person's avatar image, written by the profile page. Session-only. |

**Binary endpoints answer with bytes on success and the JSON error envelope on failure.** They are
ordinary `/api/v1` routes otherwise — same `apiAuthMiddleware`, same `apiErrorMiddleware`, same
status codes — so there is no second auth path to keep in step. Files are served through the app
rather than by handing out object-store URLs, so the bucket stays unreachable from clients.

### List query parameters

A list endpoint should validate its query string with **the feature's own search schema — the same
one the web route hands to `validateSearch`** — via `searchParamsToObject`
([src/lib/api/query.ts](../src/lib/api/query.ts)):

```ts
const search = taskSearchValidation.parse(searchParamsToObject(new URL(request.url)));
```

So `/tasks?status=todo` and `/api/v1/tasks?status=todo` accept the same vocabulary and reject the
same nonsense — a filter can be copied off a browser URL into an API request unchanged. Note
`search`, not the REST-conventional `q`. A bad filter value is then a 400, not a silently ignored
filter.

A feature with no search schema of its own can fall back to the generic `parseQueryInput`, which
validates the query's *shape* but not its values — every non-reserved key becomes a `where` filter
and an unknown value is dropped rather than rejected. Prefer a schema.

| Param | Example | Meaning |
|---|---|---|
| `page`, `pageSize` | `?page=2&pageSize=20` | Offset pagination. `pageSize` is clamped to `maxPageSize`. |
| `sort`, `order` | `?sort=createdAt&order=asc` | Defaults to `createdAt desc`. |
| `search` | `?search=report` | Search term, matched against the feature's search keys. |
| anything else | `?status=todo&status=done` | A `where` filter; repeated keys become a list. |
